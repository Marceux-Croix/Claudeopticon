# How Claudeopticon works

Claudeopticon is one hooks module, `hooks/register.tsx`, plus the modules it imports in `hooks/` (see Module layout). It has no server and no database. Each Claude Code session runs its own copy, so a pane shows only its own project and agents.

## Module layout

Each file in `hooks/` has one responsibility. `hooks.json` loads only `register.tsx`.

`register.tsx` registers the hooks and the tools. It also holds each function that calls the engine through `$`, and the session state that those functions write. `claude plugin validate` follows `$` only into functions in the same file, never across an import. It also reads a hook filter, such as a tool name, only from a constant in that file. An imported `let` cannot get a new value in the module that imports it. So the engine calls and the state they assign stay in `register.tsx`, and the other modules hold pure logic, types and constants. A constant lives in the module of the code that uses it.

## The hooks

| Hook | What the mod does |
| --- | --- |
| `session.start` | Registers `/claudeopticon` and the two tools (`report_progress`, `move_ticket`), prunes old sessions, reads the todo, opens the pane. |
| `command.run` | Runs `/claudeopticon`: scans the todo and opens the pane. |
| `prompt.context` | Adds the todo rules as a context block, unless the `rules` option is off. |
| `ui.render` | Draws the pane: SVG cards on the desktop app and VS Code, text on a terminal. |
| `tool.call` | Counts each agent's tool calls, records Claude's call summaries and each call's detail (Bash command, file path relative to the repo, Grep or Glob pattern, URL, search query, agent type and model; nothing for MCP tools; at most 300 characters; a command that matches a secret pattern is stored as "(hidden)"), rereads the todo after an edit in `.claude_todo/`, and answers `report_progress` and `move_ticket`. |
| `agent.spawn` | Adds a line to each agent's prompt that asks for progress reports, and starts the agent's row. |
| `prompt.submit` | Attaches notes for Claude: agents you named by label, moves you made by hand, IDs the mod gave or changed, the next three free ticket IDs, and claimed tickets still in progress (each at most once every 30 minutes). |
| `turn.step` | Counts the tokens of each model request, the main conversation's and each agent's, once, at the step that used them. It takes them from the step result, or from the stop chunk when the result is missing or counts nothing, and never adds both. The count goes to the session total, both token traces and, for an agent, its card. |
| `turn.complete` | Counts no tokens. For an agent it marks the end of its turn (the agent is then idle if nothing follows) and folds in its last counts. For the main conversation it ends Running on the Orchestrator card. |
| `session.compact` | Records the token count at a compaction, so the graph can start "since compact" from there. |

A clock tick each second refreshes running agents. A request that counts tokens is awaited before the step returns, so the count is drawn and stored in order, except while the store does not answer: then the model request does not wait for it. An agent missing from the agent list for 15 seconds ends with the status `ended`. Agent rows (the last 200) are saved per session, so a reload keeps start times, counts, links and progress. The mod also stores how many agents came before the first kept row (`agents-base:<session id>`), so labels count from there and A201 stays A201 after a reload. A label's font size shrinks with its length so it fits its 28 px circle with room to spare (at most 17 px of text, measured for Instrument Sans, the widest of the fallback fonts). Chat names are read up to six digits. There are 16 agent colors, most distinct first (each the OKLab color farthest from those before it). An agent takes the first color that no live agent holds when it starts, and keeps it; the color is free again from the time the agent ends or goes idle (`colorSlots` in `agent-colors.ts`, set by each `buildView`). With all 16 held, a new agent shares the color with the fewest holders, so a color can repeat but no agent waits.

An agent is idle when its turn ends (`turn.complete` with its ID) and no tool call or model request of its own follows. Claude Code keeps such an agent open until something stops it. The card shows it as Idle, out of the live count, its time and timeline bar stopped at the end of the turn, and its last command as "Last:". Its next call or request ends the idle time.

When an agent leaves the live state (completed, failed, killed or ended) and tickets linked to it are still open or in progress, the mod queues one note for Claude, once per agent, naming up to five of them and asking Claude to close each one whose work is done. It goes with the next tool result or prompt. The mod never changes a box for this.

Time limits keep one stuck call from holding the mod. One outside call (a trash command, `osascript`, `rmdir`, `mkdir`, `git`, `printenv`, `open`) or one job under the write lock waits at most 20 seconds (`RUN_LIMIT_MS`). One store call waits at most 5 seconds (`STORE_LIMIT_MS`). A call that runs over counts as failed. The call itself is not stopped, because the engine gives no way to; its late result is dropped. A failed store read is never taken for an absent key, and a failed store write is tried again, with a wait that doubles up to 5 minutes (`backoff.ts`).

The store holds the data per session (`agents`, `agents-base`, `agents-cut`, `series`, `tokens`, `orchestrator`, `orchestrator-title`, `presence`, `archive-wrote`, each followed by `:<session id>`) and `reserved:<repo root>`. The list `sessions-recent` holds the last 20 sessions, each with the time it last noted itself. A running session notes itself every 10 minutes. A session falls off the list when it is older than the last 20 and has not noted itself for an hour. Its keys are then cleared in two steps: it waits in `sessions-dropping` for 20 more minutes, so a live session whose note was lost in a race can note itself again first. The key `archived:<session id>` is no longer written (the board has no Done column); pruning still clears old ones.

**Stop** runs the `TaskStop` tool with the agent's ID. That aborts the agent's loop: no more turns, no summary.

The todo folder is scanned every 3 seconds, and fully reread once a minute.

Every todo read goes through `readTodo` and every todo write through `writeIfUnchanged`, both in `register.tsx`. `readTodo` never takes a failed read for an empty or absent file: a read that throws is "missing" only when the disk says nothing stands at the path. `writeIfUnchanged` checks the folder's trust and the file's place, then reads the file again, compares it with the text the caller worked from, and writes with no `await` between that read and the write, so an edit made meanwhile is never written over. A file that changed is skipped, and the next scan works from the new text. A file that fails to read three passes in a row is left out when new IDs are chosen (`unread-files.ts`). Two gates enforce the layers on the source: `scripts/check-reads.ts` and `scripts/check-writes.ts` fail on any todo read or write that goes around them, and on any way around the `fs.read(` and `fs.write(` text (an alias, a destructured call). The few allowed calls on files that are no todo file are listed with their reasons in `tests/read-scan.ts` and `tests/write-scan.ts`.

## Reading the todo

The mod shows the tickets of every `.claude_todo/` folder in the repo together, as if they were one todo. It finds the folders once, when it starts, with `git ls-files` (tracked, untracked and ignored folders; at most 20). From a git worktree it adds the main checkout's folders. Outside a repo, or if git fails, only the nearest folder counts. It never reads the global one in the home `.claude` folder. Each scan also looks for the nearest folder without git, so a folder made later in the session's folder or above it shows at once. Files of the same name in different folders stay two files. The ticket view draws one board for all files, with the tickets of every file in each column (files in their order break ties), and one header card with a row per file. A row shows its folder only when another row has the same name. The list view draws a card set per file. Each ticket keeps its source folder and file, so a change goes back to that file and a prompt to Claude names its real path. The files in the known folders are rescanned every 3 s and at each resync. Three buttons tidy the files. Consolidate todos moves every non-blank line of the other top-level todo files (other folders, and the central folder's extra files) into one target file in the central folder (`<root of the main checkout>/.claude_todo/`): `TODO.md` if it exists (any letter case), else the only top-level todo file, else a new `TODO.md`. Each file is a block under a `## From <place>/<file>` heading, and a clashing item ID gets the next one that no file uses, with references in the same file following. Archive files of other folders go to the same-named central archive file. The target is read again to confirm the block, and a source is then emptied only if its text is still what was copied. An empty top-level file keeps a header row that says Empty. Delete empty todos moves `.md` files with no text to the system trash (read again just before; `/usr/bin/trash`, then Finder through `osascript`, on macOS; `gio trash`, `trash-put`, then `kioclient5` on Linux; PowerShell `SendToRecycleBin` on Windows). A move counts only when the command succeeds and the file is gone, and it never falls back to an outright delete. Then it tries a non-recursive `rmdir` on the emptied `archive/` and folder. It never takes the target or `categories.json`. Windows paths (`C:/...`) pass the same trust rules. Delete duplicate tickets keeps the first of each group of top-level tickets with no indented lines under them that are identical apart from their own leading ID, removes the rest from the target, and rewrites references in the target and the central archive files. In the archive files a ticket's own leading ID never changes. Consolidate reads, writes and empties no file behind a symlink. The paths must be absolute, free of symlinks, inside the main checkout and not the global folder. All three are off in a linked worktree and when the main folder would be the global one. A line's `#T<n>` ID is the item's key. Without an ID, the key is the item's text. Outside the folder nearest to the session folder the key also carries the folder, so equal IDs in two folders stay two items. `categories.json` lives in the nearest folder only.

## IDs, numbering and the archive

A ticket ID is `#T` followed by a digit and then digits or letters, read without regard to case and ending at a word boundary, so `#T12` and `#T002A` are IDs and `#TODO` is not. Other prefixes keep the older form, letters then digits. The part after `#T` is a base-36 number (`25` is 77, `0026` is 78), so old and new IDs share one number line. The next free ID is one more than the highest value in every live and archive file of every known folder, written as 4 characters with leading zeros, and a form that starts with a letter is skipped. After `#T9ZZZ` the IDs grow to 5 characters. The number line ends at `#T20000`: a `#T` word at or past it, or with more than 6 characters after the `T`, is a plain word, so a stray tag such as `#T20241005` never moves the next IDs.

Two sessions in one repo must not give the same ID, and the engine store has only get and set, so the mod claims IDs in blocks on disk. A block is 8 ID values. A session claims a block by making an entry named for the block in a claim folder, with a create that fails when the name is taken (`mkdir` without `-p`; on Windows a file opened with CreateNew). The operating system makes that atomic, so one block has one holder. The main claim folder is `claudeopticon/id-claims` in the git common directory, the same for every worktree of the repo. When that folder cannot be made and the common directory is `<root>/.git`, the fallback is `<root>/.claude_work/claudeopticon-id-claims`. With no git at all, the primary todo folder's parent keys one folder. A session lists both folders before it claims and again after: if the other folder now holds a claim on the same block, it deletes its own claim and tries the next block. Both may give up, so a block can become a gap in the numbers, never a duplicate. A holder gives out new IDs from its block for 2 hours (`CLAIM_USE_MS`); a claim is stale after 4 hours (`CLAIM_MS`), and then another session may take the block over with the next generation's name (`<block>.<generation>`), which is just as atomic. A named ID stays reserved for 2 hours. Once an hour the mod deletes stale claim entries below the next free block, and always keeps the newest entry of each block. When no folder works, the claim fails, or 64 blocks are all held, no ID is given and a toast says so.

Each scan first numbers, then archives, in each top-level todo file of a trusted folder (inside the main checkout, not the global one, no symlink). Numbering gives each checkbox line that has no ID the next free one, right after the box, once the line has been seen without an ID for 5 seconds. Archive files are never numbered. A line that already names an ID anywhere in its text, such as a reference, keeps that as its ID and is not numbered. If numbering wrote a file, the scan starts again before the archive step, so the archive step never works from old text.

The archive step moves each top-level `- [x]` line, with the indented lines under it, to `archive/<same name>`, once every box in that block has been checked for 5 seconds. A block with an open subtask stays. Each block goes under the heading it had, the nearest heading above it outside code fences: at the end of that heading's section in the archive, or under a new copy of the heading at the end. Headings, notes and prose stay in the live file. The order is the same as Consolidate's: write the archive, read it back to confirm the blocks, read the source again, and write it without the blocks only if it did not change. A retry skips a block whose lines are already in the archive in that order. The board has no Done column and the store keeps no list of archived tickets. A file's header row counts its same-named archive file, and the Todo heading counts every archive file.

**Show completed (N)** opens the archive file of the central folder (else the primary folder) with the system's opener: `open` on macOS, `xdg-open` on Linux, `explorer.exe` on Windows, with no shell. It makes the file if it is missing, and N counts the closed tickets in every archive file. The desktop app draws a link only for `https://` addresses, so this is a button and not a link.

## Linking agents to tickets

Strongest first: the ID in the agent's description or prompt (a whole ID: `#T1` does not match `#T12`); a `report_progress` claim; a Haiku match of the task against open items (at most three); a quote of the item's text. Only running agents link.

The main conversation (the orchestrator) claims a ticket when, in this session, an Edit or Write of a todo file by the main conversation moves its box to `[~]`, when a main-conversation `report_progress` names it, or when the Send button sends it. The status button claims only a ticket whose box is already `[~]`: a status ask starts no work, and a claim on a ticket never seen in progress would never end (#T008O). A helper agent's edit or report never claims for it. A claim ends when the ticket is done or gone, or when its box goes back to `[ ]` or `[>]` after it was seen in progress, or when `move_ticket` moves it to open or queued while its box is already there (the box does not change, so no dialog shows). Claims are stored per session (`orchestrator:<session id>`), so a reload keeps them. Its card shows Running between `prompt.submit` and the main `turn.complete`, and its O tag blinks only then. Its title is the `title` the main conversation last sent with `report_progress` (helper agents' titles are ignored; at most 80 characters; stored per session as `orchestrator-title:<session id>`, cleared when it owns no tickets), else the first claimed ticket's text plus " and N more". A Bash edit of a todo file does not claim.

### Peer sessions (#T008R)

The store is one JSON file shared by every session on the machine, so sessions on one repo can see each other through it. Each session writes `presence:<session id>` = `{ v: 1, sessionId, name?, root, tickets, agentTickets, planned, seenAt }`: `root` is the main checkout's root (worktrees of one repo match), `tickets` the tickets its main conversation holds, `agentTickets` those its live agents hold, `planned` those its main conversation queued (`planned` is absent in a 0.9.16 record and reads as empty), `seenAt` the clock time of the write. A ticket is named across sessions by the absolute todo folder path, the file name and the stored item key (`ticketId`), never by the folder-qualified display key, which differs by session. The record is written when the holdings or the name change, and at least every 5 seconds (`PRESENCE_EVERY_MS`) while the session runs. Work in hand (`tickets`, `agentTickets`) counts on any box but done, and a planned claim only while the box is `[~]` or `[>]` (#T008U, #T008Y): `holdings` and `buildView` apply the same rule. `peerHolds` marks a claim `isPlanned` only when a planned list alone names it; `buildView` shows a held claim in In progress (as `heldFrom`, like a local agent's), so every board places the ticket as its owner's does, and only a live agent or the orchestrator here hides it, not an agent that finished. `peerStep` keeps the latest `peerHeld` at every read and redraws only when the claims, names, kind or silent state change; keeping it only on a change held the first `seenAt`, and every peer read as silent after 2 minutes (fixed in 0.9.18). The engine gives the mod no end event, so a session that ended is known only by its record going silent: after `PEER_DIM_MS` (2 minutes) its claims still count but are drawn dimmed, and after `PEER_IGNORE_MS` (24 hours) the record is ignored.

Planned claims (#T008U): the `tool.call` handler records, as planned (`plannedTickets`, by `ticketId`), the tickets a main-conversation Edit or Write of a todo file set to `[>]` (`newlyQueued`), and `queueStopped` records those the mod queues. Hand moves and helper edits do not. The set is stored as `planned:<session id>` and pruned on each todo read (`prunePlanned`) to the tickets whose box is `[~]` or `[>]`.

The store has no key listing, so every 5 seconds a session reads the session list (`sessions-recent`) and the `presence:<id>` of each other session in it. A record counts when it has the exact shape (lists and strings capped, malformed records ignored), names the session of its own key, has the same root and a `seenAt` within `PEER_IGNORE_MS`. A ticket this session itself holds is never counted as a peer's. `buildView` marks each other ticket as `peer` (`{ name?, isPlanned?, silentSince? }`); an in-progress ticket stays in In progress, a queued one in Queued (`isPlanned`); `ticketSvg` draws the yellow "Peer owned" pill in the bottom row left of the buttons (at half opacity when `silentSince` is set), with a `<title>` from `peerTip`: "<name> owns this" or "<name> plans to work this", plus " (inactive since HH:MM)" when silent, and returns the card with `isInteractive`, so the `Svg` is drawn in the engine's sandboxed frame where `<title>` tooltips show (#T008T), and the board keeps its Send button, which sends `peerSendPrompt` instead of `ticketPrompt` (#T008U): Claude asks the owner with SendMessage first, or, for an unnamed owner, every other session through ListAgents with the repo root, and does not claim the ticket at the press.

Notes (#T008U): `SESSION_NAME_NOTE` asks Claude once per load for the session name when it has none (none reported, none recovered from its own presence record), the session holds a ticket or a peer is on its root, and the rules line that asks for the name was never given (a session that started before 0.9.16). `plannedLine` (a planned claim the mod recorded: from an Edit or Write of the main conversation, the mod's own requeue, or an approved main-conversation `move_ticket` to queued) and `peerClaimedLine` (a ticket this session claims that a peer claims too, found in `peerStep`) queue in `pendingClaimed` and are told once with the next tool result or prompt. `report_progress` `release` (main conversation only) calls `releaseTickets`, which drops the orchestrator and planned claims on the tickets named, matched as `items` are. The name is the `session` field that the main conversation sends with `report_progress` (the rules ask for it once): a trailing " [ref]", control characters and markup are cut, at most 60 characters, the last one wins. Limits: a session that is not in the 20-session list, or whose record is older than 24 hours, is not seen; with no absolute repo root (outside git, no real folder path) a session writes and reads nothing; a dead session's `presence` key is not cleared with its other keys, it only goes stale.

## Categories

Haiku sorts open items into at most five categories, kept in `.claude_todo/categories.json`. On start it sorts unsorted items, 60 per call and up to 300. After that it sorts new items at most every 30 seconds.

**Recategorize** sends every open ticket to the same sorting prompt, ignoring the current groups. Each new group is matched to the old group it shares the most tickets with. The new groups are written only when the number of groups differs, or when at least a quarter of the open tickets would land in a group that does not match their old one. Otherwise the old groups stay, and a note shows next to the button for 4 seconds: "The current categories are correct", or "Could not recategorize" on a failure. A press while a request runs is ignored.

## Search

The search box keeps the open, queued and in-progress tickets whose text holds every word of the query, without regard to case (`searchTodo` in `view-model.ts`). It does not read the archive. Done tickets leave the board, so **Show completed** is the way to the archive.

## Secrets

Text that looks like it holds a secret is replaced with "(hidden)" before it is drawn or stored (`secrets.ts`). The surfaces are the Orchestrator summaries and details, an agent's current command and description, the stored brief of an agent's prompt, the Orchestrator title, and rows read back from an older store. A hidden line keeps the ticket IDs it names, so linking still works. The patterns are long options with a secret word, the short options of listed tools, assignments to names with a secret word, and the PowerShell forms. The rule works on the form of the text only. A secret with none of these forms is not hidden.

## Ticket buttons

`⋙` and `?` send a prompt to Claude. Every ticket has `?`. Open and queued tickets have `⋙` until it is pressed once. The manual moves (`≡` queued, `◐` in progress, `✓` done, `↪` back one column: in progress to queued, queued to open) rewrite one checkbox. A card shown in progress only because an agent works on it has no `↪`: its box is still open or queued. Each move is queued as a note that goes to Claude with its next tool result or your next message. To change a move, Claude calls `move_ticket`, which asks you and writes only on a yes.

## Queued tickets

`- [>]` is queued: the work slated next. The board shows it in the Queued column, between In progress and Open; an agent on it moves it to In progress, as for an open ticket. Where tickets of all states share one list (a category group, the list view), queued sorts after in progress and before open. Within a board column, tickets an agent works on come first, then by category in the order the categories were made, then in file order (`ticketColumns` in `view-model.ts`). **Rank by recency** (#T004F) orders each column by ticket ID value instead, highest first (`itemIdValue`, from `ticketValue` in `ticket-ids.ts`): IDs are given in sequence, so a higher value is a newer ticket. A ticket with no ID comes last, in file order. The choice lasts for the session. When one ticket is in two files, in progress wins over queued, queued over open, and open over done.

Two hooks make Claude use the column. In `tool.call`, an Edit or Write of a todo file by the main conversation that takes a ticket from `[~]` to `[ ]` (`stoppedKeys` in `stop-queue.ts`) has its box set to `[>]` under the writer lock, and the tool result carries a note. In `turn.step`, the main conversation's text (up to 20,000 characters a step) is read for ticket IDs in a sentence with a word that puts work off (`deferredIds` in `deferred-tickets.ts`); each open ticket it names gets a note once a session. The note only asks: a reply never moves a ticket.

## The top graph

The top card plots three series over the last 30 minutes: the live agent count, recorded each time it changes; all tokens since the last compaction, recorded at each model request; and tokens per minute, worked out from the token series. A request is counted once, at its own step, for the main conversation and for every agent. Within one 30 s step (`QUANT_MS`), a request that follows a rise moves that point up instead of adding one, so the rises in a step still sum to its tokens. Tokens per minute at each step is the sum of the rises in the minute before it (`RATE_MS`, 60 s); a count read back after a load is a seed and counts as no usage. A compaction adds a marker and a point at zero, and the token line breaks there. The series are stored per session (`series:<session id>`, at most 2000 points each), so a reload keeps them. A clock that once read far ahead is corrected: later points are re-timed to the clock, and a smaller step back puts the new point at the last point's time.

The agent line has the left axis. The token lines share the right side: the green column labels all tokens since compact, and the blue column, `RATE_GAP` (14 px) after it, labels tokens per minute. The rate has its own scale, fitted to its own peak, on the same 4 gridlines as the token scale (#T004E). Before 0.9.5 the rate scale was the token scale divided by 10, and the rate line drew flat along the bottom once the count reached hundreds of millions. Each scale is drawn in its line's color. The left margin mirrors the right one: the axis titles sit the same distance from their card edges, and the agent numbers sit `RIGHT_DX` (16 px) left of the plot as the green numbers sit right of it. Each axis grows only when a value would leave it, to the next step (agents 4, 6, 8, 12, 16, 24, 32 and so on; tokens 150k, 300k, 600k, 900k, 1.5M, 3M and so on, with 4 grid intervals, in k, M and B), and shrinks, to the step that holds the peak, as soon as every visible value is below half. The token axis holds the count only from the last compaction in view on (`sinceCompact` in `series.ts`). The rate axis holds the rate over the whole window: the rate does not reset at a compaction. A count segment from before that compaction that passes the top is drawn clipped at the top. It gets a zigzag break mark over the top line at its start (`clipMark` in `hero-card.ts`, at most 24 px wide) and its peak, rounded to 3 digits, in the row under the Compacted label (`clipLabelBox`). A peak label that would come within `COMPACT_CLEAR` (4 px) of a peak label drawn before it is left out, and its zigzag stays. The end labels keep clear of that peak label and of the zigzag. The token axis shows "0" at its bottom. Token reports redraw the card at most every 5 s (`CLOCK_MS`), and an idle redraw every 30 s scrolls the time axis. X positions snap to 30 s, so redraws in between send the same markup.

The mod's version (`v0.9.12`) is drawn small in the card's lower right corner. `session.start` reads it from `.claude-plugin/plugin.json` under `$.plugin.root` (`manifestVersion` in `plugin-version.ts`), so each load shows the revision that runs; a manifest that cannot be read shows none.

Each line ends in a dot. Ends less than 8 px apart (`MERGE_PX`), which includes equal values, are drawn as one larger dot split in wedges, one per line (`card-end-dots.ts`). Each end value is a label with a halo. `card-end-labels.ts` places the labels so that they keep clear of the traces, the dots, each other and the Compacted label. A label starts in its home column, just left of the dots, and may move left by up to 3 columns of 24 px. If no place there is clear, the search runs again over the whole plot width to its left edge, and a far place wins only over a place on a trace. The labels keep the vertical order of their dots, unless that would put one on a trace. The search is greedy first, top label first and bottom label first, then a bounded branch-and-bound that stops after 100,000 tries (`JOINT_TRIES`), so one draw takes tens of milliseconds in every state (it took up to 5 s before the bound). A label more than 24 px (`LEADER_PX`) from its dot gets a leader line. The placer avoids a leader through another label, and leaders are drawn under the Compacted label and the label halos. Agents are yellow (`#FACC15`, `#CA8A04` in the light theme), tokens lime (`#A3E635`, `#65A30D`) and tokens per minute blue (`#60A5FA`, `#2563EB`). The axis numbers use the card's text color. The totals line reads "total session tokens", then the agents finished, and drops words when the card is narrow. The key sits in the top row after the totals; on a narrow card it moves to its own row.

When a ticket leaves a column or a list, a transparent card of the same height takes its place, so the cards below keep their position. The spaces clear at the next press that changes the board (a filter, a view switch, a search), or after 60 s, and at most 10 are kept. A ticket's own button and the controls that change nothing on the board (Stop, the Orchestrator pages, Limit UI shift, Show finished agents, Show completed) keep them (`pressKeepsSpaces` in `ticket-spaces.ts`). A ticket that moves to a column drawn above its own (In progress or Queued over Open on a narrow pane) leaves no space: the column above grows by its card, so without a space the two cancel and the cards from its place down stay put (`above` in `columnSlots`).

## Drawing

Each card is an SVG image, drawn with its width and height, so a new card takes its room before its image loads. Its markup does not change with the clock alone, so a redraw with no new data does not reload the image. Motion is CSS and stops under `prefers-reduced-motion`. A light palette follows the system theme. Cards other than tickets are at most 960 px wide. The board's ticket columns use the full pane width, so tickets grow and shrink with the pane, and each ticket is as wide as its column, with its buttons on it. When three columns do not fit, the columns are drawn in rows of two: In progress and Queued on top, and Open under them at the full width. They stack, one under another, when a ticket would be under 300 px wide. The right axis margin measures each axis number by glyph (`labelPx` in `hero-card.ts`), so the Tokens title stays clear of the numbers.

## Limits of the mod API

- An SVG card takes no click, so buttons sit over its bottom row.
- Elements sit in text cells, so button positions are approximate.
- A card cannot scroll inside the pane, so the Orchestrator history uses paging buttons.
- On the desktop app the pane keeps its scroll offset in rows when content above the window changes, so the content you read moves. A mod with a `ui.scroll` hook does get the reader's own moves (offset, step, window and tree rows), but it cannot hold the reader's place: `$.ui.scroll` to a key moves the desktop pane without raising `ui.scroll`, so a mod cannot measure an element's row without scrolling to it, and an `Svg` key is no scroll target at all (0.9.14 tried a scroll lock on this and was withdrawn: its measures scrolled the pane in a loop). Scroll anchoring has to come from the desktop app. The mod holds heights instead (`agent-room.ts`): empty gray cards keep the agent area at its tallest height while three agent cards or fewer show, always with one trailing empty card so the count of row gaps does not change (`ROOM_SLOTS`), and the timeline is drawn with no agents, and the Orchestrator card is always as tall as a page of five entries with detail lines, drawn empty before the first call. The hold is off by default; the **Limit UI shift** button at the Orchestrator heading turns it on for the session (`isRoomHeld` in `register.tsx`, `orchestratorSvg(entries, isHeld)`), and is drawn `primary` (filled) while on. Off, the pane draws as before the hold.
